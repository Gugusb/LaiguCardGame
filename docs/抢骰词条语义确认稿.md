## 一、旧引擎抢骰流程回顾（DuelGame.java）

- 阶段流：REGISTER → DEPLOY → **DRAFT（抢骰）** → PLACE → ROUND_END。
- 双方部署完成后 `buildDraftPlan()`（L612 附近）读场上「抓取系」卡牌，生成抓取计划：
  - 先手默认抓取次数 3（每次颗数 1/2/…/2/1 对称递增），后手默认 2（每次 2/2/…）。
    见 `FIRST_DRAFT_TURNS=3` / `SECOND_DRAFT_TURNS=2`（L44-45）。
  - 计划项交替执行：先手第 1 次 → 后手第 1 次 → 先手第 2 次 → …
- `pickDie`（L516）：从共享池抓 1 颗 → 私有池；`draftTarget`/`draftTurnRemaining` 递减；
  结束条件：本次抓完 / 共享池空 / 私有池满（MAX_DICE_HELD=8）。
- 抓骰副作用（按序）：星月夜金卡补池 → 重骰判定 → DRAFT_SCORE_EXTRA 计时得分。

## 三、歧义点（待用户拍板；当前按「拟采用」执行）

- **Q1 青瓷莲花尊双词条**：目录两条目同 id，`BY_ID` 后写覆盖 → 旧引擎运行时只有第 3 批
  「抓取得分·试」生效（连拾不生效）。但总计划阶段16 明确写「青瓷莲花尊 GRAB_UP+SCORE_EXTRA」双效果。
  拟采用：**双效果并存**（把两条都算数）。若你拍板「严格以第 3 批为准」，则删掉连拾实现即可。
- **Q2 鸟音山水钟**：同理 id 重复，旧引擎运行时只有「重骰·试」生效；第 2 批「同代应（输则抽2）」被覆盖。
  拟采用：**仅重骰**（与台账一致）。
- **Q3 星月夜金卡补池**：旧引擎 `pickDie` 硬编码「场上任一方有金星月夜 → 每次抓骰后共享池 +1 随机骰」，
  不在目录词条中。拟采用：**作为金卡附加效果迁移**（每次任一方抓骰后 +1 随机骰，上限不设）。
- **Q4 重骰上限**：旧引擎 `rerollLimit += isGold ? 2 : 1`（每轮重置）。拟采用：普通 1 次/轮、金卡 2 次/轮，
  重骰在抓取判定后自动触发（无选择权），仅重骰 > 抓取点数 的骰。
- **Q5 抓取得分金卡**：DRAFT_SCORE_EXTRA 的 GoldScale=DOUBLE → 金卡 (6−点数)×10。拟采用：是。
- **Q6 次数类金卡不翻倍**：DRAFT_TURNS_UP/DOWN/SELF_TURNS_UP/OPP_TURNS_DOWN/SELF_GRAB_UP 均 RAW →
  金卡数值与普通相同（无附加效果的 4 张：天球仪/铜壶滴漏/印香囊 金卡 ≈ 普通卡）。拟采用：是。

## 四、新系统设计（拟）

1. **BattleState 共享骰池模型扩展**（已有 sharedPool 值列表）：
   - `DraftPlan`：双方抓取次数 turns[2]、每次颗数 sizes（按次序表）、计划项序列；
   - `rerollUses`（本轮已用重骰次数，回合开始清零）；
   - 抓取动作 `grabDie(side, poolIdx)` 迁入新核心：扣骰 → 记账 → 派发 DRAFT 事件（重骰/得分/补池由卡类响应）。
2. **OnDraft 接口落地**：`NewCardBattle.buildDraftPlan()` 遍历场上 OnDraft 卡收集次数/颗数修正
   （对齐旧 buildDraftPlan 的 fMod/sMod/selfMod/oppMod/grabMod 汇总）；`pickDie` 后派发
   `BattleEvent.Type.DRAFT`（带抓取点数），卡类 onDraft/onEvent 响应重骰与得分。
3. **流程接新核心**（总计划第 3 点）：旧 DuelGame 的 DRAFT 阶段状态存储保留（存档兼容），
   计划构建与抓骰副作用改调新核心（`NewCardCoreSwitch.enabled()` 时）；回滚开关关 = 旧路径原样。
4. **清空白名单**：`NewCardCoreSwitch.UNMIGRATED_IDS`、`CardRegistryValidator.PENDING_DRAFT_INFRASTRUCTURE`、
   台账/Stage11 未迁移清单 → 158/158 全部由新系统实现。
